# 面向数据清洗的安全模型训练系统

更新时间：2026-10-26

本文档用于面试、项目答辩和项目演示。内容以当前代码实现为准，明确区分已经落地的能力、当前演示范围和后续规划，避免把规划内容误述为已完成能力。

## 1. 项目概述

这是一个由网络安全竞赛项目重构而来的安全模型训练实验平台。平台当前围绕 LDD 训练前防御算法，完成从实验资源登记、任务创建、参数校验、Python 算法执行、运行监控、失败重试、实验报告到清洗数据集导出的完整闭环。

项目解决的核心问题不是单纯“把一个 Python 脚本放到网页上运行”，而是把一次安全算法实验抽象成可管理、可追踪、可恢复的业务任务：

- 任务开始前确认数据集、算法和参数有效。
- 任务运行过程中隔离进程、日志和产物。
- 任务失败后可以重试，且不会覆盖上一次运行现场。
- 实验完成后可以解释本次运行使用了什么参数、资源和运行环境。
- 算法输出的保留索引可以进一步重建为可下载的干净数据集。

当前系统只开放 LDD。VS 对比算法、训练中防御和训练后防御暂不进入主流程，后续通过统一执行器接口扩展。

## 2. 我在项目中的实际工作

面试时可以将自己的工作概括为“把一个研究型安全算法工程改造成可演示、可追踪的后端任务平台”，具体包括：

1. 梳理原竞赛项目中的数据集、算法脚本、参数和结果产物，划分平台职责与算法职责。
2. 设计训练前防御任务模型和任务状态机，补充启动、取消、失败、重试和查询接口。
3. 设计 `DefenseTaskExecutor` 执行器边界，通过标准 JSON 请求和结果文件调用外部 Python/PyTorch 算法。
4. 将 LDD 接入 VaB 原始工程，在不直接修改研究代码的前提下完成参数映射、任务目录隔离和结果协议适配。
5. 实现执行快照、资源指纹、运行环境记录和任务产物保留，保证历史实验可以解释和复现。
6. 实现 Python 进程超时终止、取消回收、应用重启恢复、执行池准入和任务配额。
7. 完成前端任务中心、进度页、任务详情、日志、报告和清洗数据集导出页面。
8. 编写服务层和策略层测试，并完成一次小批次、小轮次的 LDD 工程链路验证。

## 3. 用户与业务场景

### 3.1 主要用户

- 算法研究人员：配置数据集和 LDD 参数，启动实验并查看清洗效果。
- 平台管理员：维护数据集、算法、模型和超参数模板等实验资源。
- 论文或答辩使用者：查看运行过程、实验报告和清洗后数据集。

### 3.2 典型场景

用户登记 CIFAR-10 数据集和 LDD 算法，创建一次指定攻击方式、批次大小、训练轮数和清洗参数的任务。平台在后台执行 Python 算法，前端展示任务状态和日志。任务完成后，用户查看 LDD 指标、参数快照和运行环境，并按某个隔离比例导出清洗后的 CIFAR-10 子集。

## 4. 完整业务流程

```text
登录平台
  -> 登记数据集、算法和超参数模板
  -> 创建 LDD 训练前清洗任务
  -> 校验资源、算法阶段和参数
  -> 合并有效配置并生成执行快照
  -> 执行配额准入
  -> 原子领取 pending 任务
  -> 生成 run_id、attempt 和独立运行目录
  -> 事务提交后派发 Python 进程
  -> VaB 适配器调用 LDD.py
  -> 写入 stdout/stderr、result.json 和索引等产物
  -> 校验结果协议并更新任务状态
  -> 前端轮询进度、日志和结果
  -> 查看实验报告
  -> 根据保留索引异步重建并下载干净数据集
```

### 4.1 资源配置

平台使用数据集、算法、模型和超参数模板作为可复用资源。任务启动时不会只保存资源 ID，而是将资源名称、路径、修改时间、文件大小和摘要等信息冻结到执行快照中。

LDD 有效配置按以下顺序合并：

```text
算法默认配置 -> 超参数模板配置 -> 任务自定义参数
```

后端对参数执行对象类型、白名单、必填项、整数约束和数值范围校验，避免错误配置进入 Python 执行阶段。

### 4.2 任务启动

启动接口进入 `PreDefenseService` 后，先检查任务状态和资源引用，再执行单机任务配额校验。只有 `pending` 任务可以被数据库条件更新原子领取为 `running`，从而避免用户重复点击启动造成同一任务被执行多次。

每次启动或重试都会生成：

- `run_id`：本次运行的唯一标识。
- `attempt`：第几次尝试。
- 独立执行目录：保存本次请求、结果、日志和产物。
- 参数与资源快照：记录启动时的真实输入。
- 配额快照：记录当时的运行任务数、用户任务数和执行池状态。

数据库事务提交成功后才派发外部 Python 进程，避免数据库回滚但算法进程已经启动。

### 4.3 Python 算法执行

Java 后端不直接调用 `LDD.py` 内部函数，而是调用统一的 `DefenseTaskExecutor`。当前实现由 `PythonLddTaskExecutor` 启动外部 Python 进程：

```text
PreDefenseTaskCommandService
  -> DefenseTaskExecutor
  -> PythonLddTaskExecutor
  -> algorithm-runtime/vab/algorithm_entry.py
  -> VaB 外部工程中的 LDD.py
```

适配器负责将平台配置映射到原始算法代码、重定向输出目录、关闭交互式绘图，并最终写出标准化 `result.json`。平台只依赖标准请求和结果协议，不依赖 LDD 内部实现细节。

### 4.4 状态与异常处理

训练任务状态为：

```text
pending -> running -> success
                    -> failed -> pending（受控重试）
                    -> canceled
```

任务运行中的进度、结果和结束回调必须匹配当前 `run_id`。旧运行即使因为超时或取消产生迟到回调，也不能覆盖当前任务状态。

当前已经处理的异常包括：

- Python 正常退出但结果文件缺失。
- 结果 JSON 格式错误或协议字段不完整。
- Python 进程超时。
- 用户取消任务。
- 执行池队列已满。
- 应用重启导致任务失去原外部进程。
- 任务资源或参数不再满足启动条件。

失败任务保留错误码、失败原因、日志路径和运行目录，用户可以从详情页执行重试。

### 4.5 结果与报告

成功任务会保存清洗结果 JSON，前端报告页展示：

- 任务概览和最终状态。
- 每次执行尝试及其 `run_id`、`attempt`。
- 有效参数和资源快照。
- 数据集、算法和超参数信息。
- 清洗样本数量、保留比例和 LDD 指标。
- Python、PyTorch、NumPy、CUDA、GPU 等运行环境。
- stdout/stderr 日志和 PNG 产物。
- 清洗数据集导出任务及其下载状态。

需要强调的是，当前小批次、小轮次运行用于验证工程闭环，不直接作为论文正式实验结论。

### 4.6 清洗后数据集导出

LDD 输出保留样本索引，例如 `selected_indices_<ratio>.npy`。平台不直接把索引文件当作最终数据集下载，而是：

1. 校验索引文件位于当前任务产物目录内。
2. 读取原始 CIFAR-10 训练数据。
3. 根据索引提取保留样本和标签。
4. 生成图片、标签、索引和元数据。
5. 压缩为 ZIP 文件。
6. 通过异步导出任务提供进度查询和下载。

导出任务有独立状态、失败重试和唯一约束幂等；当前迁移版尚未实现导出任务的应用启动恢复扫描。

## 8. 面试中可以强调的工程取舍

### 为什么不把 Python 算法直接写进 Web 请求？

因为训练和清洗任务耗时不可控，直接占用 HTTP 请求线程会导致超时、进程无法回收、失败难以追踪。平台将算法运行独立为异步任务，并保存任务状态、日志和产物。

### 为什么需要 `run_id` 和 `attempt`？

因为任务支持取消、超时和重试。没有运行标识时，旧进程的迟到回调可能覆盖新一次重试结果。`run_id` 标识具体执行，`attempt` 标识执行次数，二者配合任务条件更新实现旧回调隔离。

### 为什么要保存执行快照？

因为数据集路径、超参数模板和 Python 环境都可能变化。快照将启动时的真实输入固化下来，使报告能够解释“这次实验到底使用了什么”。

### 为什么按索引重建清洗数据集？

LDD 的结果是保留样本索引。平台根据索引从原始 CIFAR-10 数据中提取样本，避免把运行期中间张量直接当成数据集，也能让导出结果包含图片、标签和重建元数据。

### 当前系统距离生产级还有什么差距？

当前是单机演示和实验平台，使用 JVM 内有界执行池和本地 Python 进程，尚未引入分布式 worker、容器级资源隔离、对象存储和消息队列。这个边界在项目文档中已经明确，后续可以在不改变领域协议的前提下升级执行层。

## 9. 一分钟项目介绍

我参与开发的是一个面向数据清洗的安全模型训练系统。它把网络安全竞赛中的 LDD Python 算法接入可视化实验平台，当前主要负责训练前数据清洗。用户登记 CIFAR-10 数据集和算法参数后创建清洗任务，Spring Boot 在事务提交后通过有界线程池调度 Python/PyTorch 进程执行 LDD，并在 MySQL 中保存任务状态、参数快照和实验结果。资源目录使用 Redis 缓存，MySQL 保持事实数据源，缓存不可用时回源查询。针对任务超时、取消、重试以及 Python 进程回调延迟的问题，系统使用 `run_id`、`attempt`、任务专属目录和数据库条件更新，避免不同执行尝试互相覆盖。任务完成后，前端展示清洗指标、日志、运行环境和报告，并根据 LDD 输出的保留索引异步重建和下载干净 CIFAR-10 子集。当前系统完成的是 LDD 工程闭环；RabbitMQ/Kafka 和其他防御算法的真实执行尚未接入。
